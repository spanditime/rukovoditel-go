# Поля и значения Rukovoditel REST API

Этот раздел дополняет [основной справочник API](API.md). Имена типов и
JSON-формы ниже получены read-only запросами к одному тестовому серверу
Rukovoditel 3.7 с сущностями 1 («Пользователи») и 39 (тестовая «Задача»).
Версия сообщена владельцем сервера. Наблюдение одного поля не задаёт
правила для всех полей этого типа или других версий.

## Как получить описание поля

Form POST содержит общие параметры авторизации и:

```text
action=get_entity_fields&entity_id=39
```

В `data` пришёл объект: ключ каждого свойства — строковый ID поля,
значение — объект его описания. Для всех 48 проверенных полей строковый
ключ совпадал с `id` внутри описания. У сущности 1 было 25 полей, у
сущности 39 — 23. Порядок свойств JSON не является частью контракта.

Обезличенный фрагмент ответа для поля 419 сущности 39:

```json
{
  "status": "success",
  "data": {
    "419": {
      "id": "419",
      "type": "fieldtype_dropdown",
      "name": "<удалено>",
      "short_name": "<удалено>",
      "is_heading": "<удалено>",
      "tooltip": "<удалено>",
      "is_required": "<удалено>",
      "required_message": "<удалено>",
      "configuration": "<удалено>"
    }
  }
}
```

Это **фрагмент и редакционная маска**, а не полный ответ и не fixture
для сравнения байт в байт. Сохранены реальные имена ключей, ID и `type`;
замаскированные значения не следует трактовать как допустимые значения
поля. В первом поле сущности 1 `is_heading` и `is_required` были `null`,
в первом поле сущности 39 — строками. Поэтому даже эти два свойства
нельзя объявлять только строками или только boolean.

| Ключ описания | Наблюдаемый JSON-тип | Что можно утверждать |
| --- | --- | --- |
| `id` | string | Строковый ID поля; совпал с ключом объекта у проверенных полей. |
| `type` | string | Имя типа вроде `fieldtype_dropdown`; это идентификатор сервера, не Go-тип значения записи. |
| `name`, `short_name`, `tooltip`, `required_message` | string в первых проверенных объектах | Текстовые свойства; пустота и локализация не исследованы. |
| `is_heading`, `is_required` | string или null в проверенных объектах | Не приводить автоматически к `bool` без проверки значений и версий. |
| `configuration` | string в проверенных объектах | Часть строк разбирается как JSON-объект, часть — нет; общая схема не установлена. |

Из 25 значений `configuration` сущности 1 как JSON-объект разобрались
13; у сущности 39 — 17 из 23. Это только результат синтаксического
разбора строк, не описание их смысла.

### Как узнать поля, помеченные обязательными

В ответе `get_entity_fields` для сущности 39 у четырёх полей
`is_required` был **строкой** `"1"`:

| ID | `type` | Прочие наблюдения |
| --- | --- | --- |
| 418 | `fieldtype_input` | `configuration` — строка с JSON-объектом; среди ключей есть `default_value`, `is_unique`, `maxlength`. |
| 420 | `fieldtype_users` | `configuration` — строка с JSON-объектом; есть `display_as`, `use_groups`. |
| 423 | `fieldtype_input_date_extra` | `configuration` — строка с JSON-объектом; есть `default_value`, `date_format_in_calendar`, `timepicker`. |
| 426 | `fieldtype_users_approve` | `configuration` — строка с JSON-объектом; есть `display_as`, `run_process`, `use_signature`. |

Для этого экземпляра практический способ обнаружить такие поля —
получить metadata сущности и отобрать описания с
`is_required == "1"`. В других полях сущности 39 встречалось `"0"`, а
в ранее проверенном первом поле сущности 1 — `null`; трактовка всех состояний не
подтверждена. `required_message` присутствует как строковое свойство
описания, но её текст в документацию не переносится.

Признак `is_required="1"` не доказывает, что REST `insert` валидирует
поле именно так же, как форма веб-интерфейса. На тестовом сервере 3.7
вставка с заполненными полями 418, 420, 423 и 426 без родительского ID
вернула HTTP 500. После добавления документированного
`items[parent_item_id]=1366` тот же probe успешно создал и удалил
запись. `parent_item_id` не был отдельным полем с `is_required="1"` в
metadata: контекст иерархии надо выяснять отдельно. Два запуска не
доказывают универсальную обязательность родителя. Подробности — в
[API.md](API.md#insert).

## Варианты поля (`get_field_choices`)

Дополнительные параметры запроса:

```text
action=get_field_choices&entity_id=39&field_id=419
```

Для `fieldtype_dropdown` 222 сущности 1 получен массив из 2 вариантов,
для поля 419 сущности 39 — из 5. Поле `fields_id` во всех вариантах
этих двух ответов совпадало со строковым ID запрошенного поля.

Обезличенный фрагмент `data` для поля 419, показывающий **форму** одного
варианта:

```json
[
  {
    "id": "<удалено>",
    "parent_id": "<удалено>",
    "fields_id": "419",
    "is_active": "<удалено>",
    "name": "<удалено>",
    "icon": "<удалено>",
    "is_default": "<удалено>",
    "bg_color": "<удалено>",
    "sort_order": "<удалено>",
    "users": "<удалено>",
    "value": "<удалено>",
    "filename": "<удалено>",
    "level": 0
  }
]
```

`level: 0` здесь — маска числового значения, не цитата ответа. У
первого варианта 419 все перечисленные свойства, кроме `level`, были
строками; `level` был числом. У первого варианта 222 `is_default` и
`sort_order` были `null`. Значит, нельзя объявлять для этих свойств
единый обязательный строковый тип. Пустой список вариантов и запрос
`get_field_choices` для других типов полей пока не проверены.

## Поля в `select` и при записи

Документированный запрос записи использует `field_<ID>`, например
`items[field_419]` или `data[field_419]`. В ответе `select` поля
появлялись под строковым ID без префикса: `"419"`. Кроме того, на
сервере 3.7 встречались дополнительные ключи вроде `"419_db_value"`.
Их структура и семантика по типам полей не исследованы; internal API
сохраняет исходные ключи. Пример:

```json
{
  "status": "success",
  "data": [
    {
      "id": "<удалено>",
      "419": "<удалено>",
      "419_db_value": "<удалено>"
    }
  ]
}
```

Это только фрагмент формы ответа `select` сущности 39. Маски не
подтверждают JSON-тип соответствующих значений. Для схемы параметров
`select` и фильтров см. [API.md](API.md#select).

При отдельном `select` с `rows_per_page=1` на сервере 3.7 первая
запись каждой сущности содержала ключи всех перечисленных в таблицах
metadata полей, **кроме** `fieldtype_action` (ID 1 и 412). Значения под
этими числовыми ключами в обеих первых записях были JSON-строками —
включая поля с именами `fieldtype_input_numeric`, `fieldtype_formula`,
`fieldtype_attachments` и `fieldtype_todo_list`. Это наблюдение одной
записи каждой сущности, а не правило сериализации этих типов. Помимо
числовых ключей присутствовали системные `id`, `created_by`,
`parent_item_id`, `date_added`, `date_updated` и дополнительные
`<ID>_db_value`; у сущности 1 также был `6_multiple_groups`. Форматы
значений дополнительных ключей не установлены.

## Следствие для интерфейса `api`

Параметры известных запросов уже закреплены методами `GetEntityFields`
и `GetFieldChoices`. Для ответов сейчас сохраняется `json.RawMessage`:
наблюдались строковые ID, `null` наряду со строками в отдельных
свойствах, непрозрачная строка `configuration` и дополнительные ключи
`select`. Нельзя без потерь объявить единый Go-тип для всех этих
значений по одному серверу и одной записи. Инвентарь `type` полезен для
будущего разбора metadata, но не должен превращаться в закрытый enum:
сервер может вернуть тип, которого нет в этих двух сущностях.
