# Go-клиент первой версии

REST-формат описан в [API.md](API.md), серверные наблюдения и открытые
вопросы — в [RESEARCH.md](RESEARCH.md). Запускаемые примеры находятся в
[`examples`](../examples), краткое руководство — в [README](../README.md).

## Пакеты и границы

| Пакет | Назначение |
| --- | --- |
| Корневой `rukovoditel` | Фасад одного клиента и кэша: `New`, `Refresh`, `Register`, `Repository[T]`, `Client`. |
| `api` | Form POST, общий envelope, CRUD и дополнительные actions; имена и значения полей сохраняются в формате сервера. |
| `schema` | Явные снимки metadata, привязка Go-структуры к ID сущности и полей. |
| `orm` | Ограниченные типизированные операции над зарегистрированной моделью. |

Каждый сетевой метод принимает `context.Context`. `api.NewClient` не
выполняет запрос; ему нужны полный endpoint, key, username и password.
`Config.HTTPClient` позволяет передать свой HTTP-клиент; по умолчанию
используется timeout 10 секунд. Form POST выбран по умолчанию.
`Config.Encoding=api.JSONEncoding` меняет тело запроса, но поддержка
JSON всеми actions не подтверждена. `Client.Do` оставляет возможность
передать дополнительные параметры без объявления их типизированным
контрактом. Ошибки HTTP и API доступны как `api.HTTPError` и
`api.APIError`; их сырые тела могут содержать данные сервера.

`api.SelectParams.Page` передаёт положительный номер страницы как `page`.
Он проверен для первых трёх страниц на тестовом сервере 3.7. Используйте
его вместе с `RowsPerPage`; автоматического полного обхода нет.
`orm.Query[T].Page(n)` передаёт тот же параметр для типизированной выборки;
`OneResponse` и `All` по-прежнему читают один ответ. Команда
`rukovoditel-inspect` принимает `-page N` и команды `n`/`p` при просмотре
записей.

Для просмотра своей установки используйте отдельную команду
[`rukovoditel-inspect`](../cmd/rukovoditel-inspect/README.md): она
показывает сущности, поля выбранной сущности, одну выборку записей и
сырой объект выбранного поля или записи. В Go-коде
`SchemaCache.ListEntities(ctx)` возвращает
наблюдавшиеся ID, имена и сырой объект без изменения кэша;
`Refresh(ctx, entityID)` загружает полный снимок одной сущности.

## Снимок metadata

`schema.NewSchemaCache(client)` создаёт пустой кэш схем. `Refresh(ctx,
entityID)` запрашивает `get_entities` и `get_entity_fields` для явного ID,
после успешного разбора заменяет снимок целиком. `Get(entityID)` возвращает
копию снимка и признак его наличия без сетевого запроса. Кэш не имеет TTL:
после изменения схемы вызывающий код должен явно вызвать `Refresh`.
`RefreshAll(ctx)` один раз получает список сущностей, затем отдельно
запрашивает поля каждой сущности и заменяет весь кэш после успешной
загрузки. Если один запрос или разбор ответа завершился ошибкой, весь
прежний кэш сохраняется. Сущности, которых нет в новом списке, удаляются
из кэша. Сервер может изменить схему между запросами, поэтому полный
снимок кэша не является атомарным снимком состояния сервера.
Неуспешное обновление оставляет предыдущий снимок. Удалённые поля исчезают
из нового снимка, поэтому регистрацию моделей после обновления следует
проверять заново. Конкурентное чтение безопасно; каждый вызов возвращает
целый снимок до или после обновления.

`Schema.Entity` содержит наблюдавшиеся `id`, `name`, `notes`, числовой
`SortOrder` и путь положительных ID `Path`. Методы `Level()` и
`ParentID()` вычисляют уровень и ID последнего предка из `Path`;
для корня `ParentID()` возвращает 0. Сырые `parent_id`, `level` и
`group_*` доступны через `Raw`. На тестовом сервере 3.7 корневой
`parent_id` был строкой `"0"`; форма других версий не проверена.
`Schema.Fields` —
поля по числовому ID с `ID`, `Type`, `Name`, `ShortName`, `IsHeading`
и `IsRequired`. Два признака истинны при JSON `"1"`, `1` или `true`;
прочие и отсутствующие значения дают `false`. `Schema.HeadingField()`
возвращает помеченное `IsHeading` поле с наибольшим ID или признак
отсутствия; это детерминированное правило клиента, а не подтверждение
того, как сервер строит заголовок записи.
`FieldMetadata.ShortNameOrName()` возвращает короткое имя, а при пустом
`ShortName` — исходный `Name`; оба исходных поля сохраняются. В каждом
описании есть `Raw` с остальными свойствами исходного JSON-объекта.
Тестовые ответы воспроизводят обезличенную **форму** наблюдений сервера
3.7 из [RESEARCH.md](RESEARCH.md) и [FIELDS.md](FIELDS.md), включая неизвестные свойства;
значения имён и дополнительные свойства в тестах вымышлены. Ответы других
версий и полнота схемы не установлены. Отсутствие ID в успешно разобранном
списке `get_entities` даёт локальную ошибку «absent from metadata response»;
она не доказывает, что сущности нет на сервере — возможны ограничения
доступа. Ошибки HTTP/API по-прежнему возвращаются клиентом отдельно.

## Типизированные фильтры

Типизированный `orm.Query` поддерживает `Search` для привязанного
`fieldtype_input`, `Empty` для input/dropdown/numeric/date,
`Choice` для dropdown, `DateRange` для `fieldtype_input_date_extra`
и `NumericCompare` (`>` с целым значением) для `fieldtype_input_numeric`.
Имена полей Go-модели разрешаются в ID из явного снимка metadata.
Методы отклоняют неподходящий тип и некорректное значение до HTTP-запроса.
Несколько условий передаются вместе как отдельные ключи `filters`.
Их совместное применение проверено для Search + Choice на одном тестовом
сервере 3.7; других сочетаний этот опыт не подтверждает. Каждый метод допускает
одно условие на поле; повторный вызов для того же поля заменяет прежнее.
`OneResponse` возвращает только один ответ сервера, без обхода страниц.
`All` оставлен как совместимый alias с той же границей. Поддержанные
формы проверены локально по wire format и read-only probe на тестовом
сервере 3.7; выводы probe ограничены указанными сущностями и полями.

## Привязка модели

`schema.RegisterModel(snapshot, prototype)` привязывает экспортируемые поля
структуры по тегу `rukovoditel:"418"` к явному ID поля из снимка.
`rukovoditel:"id"` допускает `int64`, `string` или `json.RawMessage` для системного ID;
`rukovoditel:"-,raw"` на `map[string]json.RawMessage` сохраняет все
непривязанные ключи ответа. Повторный тег, отсутствующий ID и неподдерживаемый
Go-тип дают ошибку регистрации. Для отдельной привязки после обновления снимка модель следует
зарегистрировать снова.

`Model.Decode` принимает сырую строку `select` как `map[string]json.RawMessage`
и копирует JSON-значения в поля `json.RawMessage` или `*json.RawMessage`.
Для привязанного поля ключ `<ID>_db_value` имеет приоритет перед `<ID>`;
если первый выбран, исходный `<ID>` остаётся в `-,raw`. Поле Go-типа
`string` допускается для чтения JSON-строки у обычных полей; JSON `null`
и другие типы дают ошибку, чтобы не терять различие значений. Для связей
`string` означает одиночный ID; пустое значение и `null` дают пустую
строку. Если нужно сохранить точное wire-значение, используйте
`json.RawMessage`.
Отсутствующий ключ оставляет нулевое значение, явный JSON `null` сохраняется
как `null`, в том числе через ненулевой указатель. Непривязанные ключи
сохраняются в поле `-,raw`; если оно не объявлено, вызывающий код должен
сохранить исходную строку самостоятельно. Имена ответа — числовые строки
вроде `"418"`, без переименования на уровне `api`.

`Model.EncodeWrite` кодирует только JSON-строки для полей
`fieldtype_input` как `field_<id>` со строковым form-значением. Пустая
строка передаётся явно; пустой `RawMessage` и `nil`-указатель опускаются.
JSON `null`, поля иных типов (включая связи и вложения) и отсутствующие в
текущей схеме поля дают ошибку. Системный `id` и сырые непривязанные поля
не попадают в запись. Нельзя выводить из metadata доступность поля для
записи: окончательное решение принимает сервер, а его ошибку возвращает
низкоуровневый клиент. Эта привязка не выполняет HTTP-запросов.

`fieldtype_formula` при типизированной записи отклоняется как поле только
для чтения. `string`-привязки также доступны только для чтения: у них нет
отдельного признака «не передавать» для безопасного частичного обновления.

Тип поля модели определяет детализацию связи. `int64` и `string` получают
один ID, `[]int64` и `[]string` — список ID без дополнительных запросов.
Для `parent_item_id` доступны одиночные `int64` и `string`. Эти привязки
читают `*_db_value`, а родителя — из системного `parent_item_id`; модель
целевой сущности регистрировать не нужно. При нескольких ID в одиночной
привязке возвращается ошибка. ID-привязки доступны только для чтения.

Для `fieldtype_users`, `fieldtype_users_approve`, `fieldtype_users_ajax`,
`fieldtype_entity` и `fieldtype_entity_ajax` можно привязать вложенную
Go-структуру, указатель, `[]T` или `[]*T`. Одиночная структура требует
один ID, срез принимает список ID через запятую в `*_db_value` и
сохраняет порядок. Для родителя записи используется системный тег
`rukovoditel:"parent_item_id"` с вложенной структурой или указателем.

```go
type User struct {
    ID   string `rukovoditel:"id"`
    Name string `rukovoditel:"34"`
}
type Project struct {
    ID string `rukovoditel:"id"`
}
type Task struct {
    ID        int64   `rukovoditel:"id"`
    Approvers []User  `rukovoditel:"426"`
    Parent    Project `rukovoditel:"parent_item_id"`
}

// Только ID: регистрация User и Project для чтения не требуется.
type TaskIDs struct {
    ID          int64   `rukovoditel:"id"`
    ApproverIDs []int64 `rukovoditel:"426"`
    ParentID    int64   `rukovoditel:"parent_item_id"`
}
```

Здесь ID полей — пример: для конкретной установки их нужно сверить с metadata.
Сначала загрузите схемы и зарегистрируйте модели связанных сущностей,
затем схему и модель задачи. Для пользовательских связей целевая сущность — 1;
для `fieldtype_entity` и `fieldtype_entity_ajax` её ID берётся из
`configuration.entity_id`, для `parent_item_id` — из пути сущности в
metadata. `orm.Get` и `Query.OneResponse` берут ID записей из
`*_db_value` (для родителя — непосредственно из `parent_item_id`) и
выполняют отдельные `select` с `filters[id]`.
Несколько ID у одиночной привязки, отсутствие `*_db_value` при
непустом основном значении, отсутствующая регистрация целевой модели и
неоднозначный ответ дают ошибку. Исходные ключи связи сохраняются в
`-,raw`; прямой `Model.Decode` для вложенной модели возвращает ошибку —
нужен `DecodeWithRelations` с resolver или ORM. Дозагрузка может вызвать
по одному дополнительному запросу на каждый уникальный ID связанной записи
в одном вызове, повторные ссылки переиспользуют полученную строку. Между
вызовами результат не кэшируется. Дозагрузка не даёт
атомарного снимка между запросами. Пустые строки, `null` и одиночный `0`
оставляют связь пустой. Другие форматы списка и запись связей через
типизированный ORM пока не поддержаны.

Системные ключи `date_added` и `date_updated` можно привязать к
`time.Time`, `*time.Time`, `string` или `json.RawMessage`.
`created_by` можно читать как одиночный ID (`int64`/`string`), сырой JSON
или вложенную модель пользователя сущности 1. Вложенная модель требует
регистрации модели пользователя и отдельного `select`; ID-привязка её не
требует. Прямой resolver `DecodeWithRelations` получает `fieldID=-1` для
`created_by` и `fieldID=0` для `parent_item_id`.

```go
type TaskDates struct {
    Added     time.Time  `rukovoditel:"date_added"`
    Updated   *time.Time `rukovoditel:"date_updated"`
    CreatorID int64      `rukovoditel:"created_by"`
    Due       time.Time  `rukovoditel:"423"`
}
```

`time.Time` и `*time.Time` также поддерживаются для наблюдавшихся типов
`fieldtype_input_date_extra`, `fieldtype_input_datetime`,
`fieldtype_date_added`, `fieldtype_date_updated` и
`fieldtype_user_last_login_date`. Разбираются строки `ДД.ММ.ГГГГ`,
`ДД.ММ.ГГГГ ЧЧ:ММ` и документированный пример `ММ/ДД/ГГГГ ЧЧ:ММ`.
Пустая строка и `null` дают нулевой `time.Time` или `nil`-указатель;
неизвестный формат вызывает ошибку. Ответ API не содержит часового пояса:
дата и время сохраняются как компоненты с локацией UTC, без утверждения,
что исходный момент был в UTC. Для точного исходного значения используйте
`json.RawMessage`. Эти типизированные даты и системные поля доступны
только для чтения.

Для `fieldtype_dropdown` `schema.Choice` (или `*schema.Choice`, срез этих
типов для нескольких вариантов) получает ID из `<ID>_db_value`, а имя и
сырой объект варианта — из `get_field_choices`. `SchemaCache.Choices(ctx,
entityID, fieldID)` читает варианты явно; ORM загружает их при
типизированном чтении и переиспользует в пределах одного `Get` или
ответа `Query`. `int64`/`string` и их срезы по-прежнему возвращают только
ID без запроса вариантов. Если ID записи отсутствует среди вариантов,
`Choice` сохраняет ID, но оставляет `Name` пустым и `Raw=nil`.
При прямом использовании `schema.Model` для `Choice` и `items_by_query`
нужен `DecodeWithLookups` с соответствующими callbacks;
`Model.Decode` без них сообщает об отсутствии resolver.

`fieldtype_items_by_query` можно привязать к `[]T`/`[]*T` для вложенных
моделей либо к `[]int64`/`[]string` для одних ID. Его `select`-значение на
проверенном сервере содержит отображаемый текст без ID записей. При
точном условии `e.parent_item_id=[id]` ORM получает ID через `select`
целевой сущности с фильтром `parent_item_id` и `limit=0`. Для других
SQL-условий вызывающий код задаёт
`repo.WithItemsByQueryResolver(func(ctx, sourceEntityID, sourceItemID int64,
field schema.FieldMetadata, targetEntityID int64) ([]int64, error) { ... })`.
Функция получает исходную metadata поля и возвращает ID в нужном порядке;
ORM затем дозагружает модели, если они запрошены. Без resolver для такого
условия возвращается ошибка. Для ID-среза модель целевой сущности
регистрировать не нужно. Исходный отображаемый текст остаётся доступным
через `json.RawMessage` или `-,raw`. Консистентность между запросами и
полнота выборки при изменении данных не гарантированы.

Для устойчивой связи типа с сущностью используйте `cache.Register(entityID,
Task{})` после загрузки снимка. Кэш хранит пару Go-тип → `entityID`;
`cache.ModelFor(Task{})` возвращает её. Повторная регистрация того же типа
вызывает ошибку. При `Refresh` и `RefreshAll` кэш проверяет, что все
привязанные ID полей существуют и их `type` не изменился. Если проверка
не прошла, метод возвращает ошибку с ID поля, а прежний снимок остаётся
в кэше. `RefreshAll` также отклоняет удаление зарегистрированной
сущности. Новые непривязанные поля не ломают привязку. Проверка
происходит только при явном обновлении; изменение схемы на сервере
между обновлениями кэш не обнаруживает. Прямой `RegisterModel` создаёт
отдельную привязку без регистрации в кэше и такой проверки при обновлении.

## Типизированные запросы

`orm.NewRepository[T](client, cache)` использует ранее зарегистрированную
модель и снимок схемы. `Get` отправляет `filters[id]`; `Insert`, `Update` и
`Delete` используют документированные действия и форматы записи. Для
`Update`/`Delete` требуются явные положительные ID; несколько ID могут
затронуть несколько записей. `Query.Search` разрешает имя поля Go-структуры
в ID поля и отправляет `condition=search`. `RowsPerPage` задаёт размер
одной страницы ответа. `Sort` всегда возвращает ошибку, поскольку формат
сортировки не подтверждён. Автоматического обхода страниц нет.

Локальные wire-тесты проверяют методы обёртки, отказ от сортировки и
защиту критериев записи. Обезличенный результат прежнего серверного
сценария сохранён в [RESEARCH.md](RESEARCH.md).
