# Rukovoditel REST API --- известный контракт

Этот документ фиксирует сведения из перечня методов Rukovoditel,
доступных примеров запросов и проверок на тестовом сервере 3.7. Полного
официального описания схем запросов и ответов у нас нет. Документ нужен
прежде всего для реализации Go-клиента; где источник — только один
сервер, это явно указано.

Подробности о `get_entity_fields`, наблюдавшихся `type` и вариантах
полей находятся в [FIELDS.md](FIELDS.md). Запускаемые примеры клиента:
[`examples/metadata`](../examples/metadata/README.md) и
[`examples/lowlevel`](../examples/lowlevel/README.md).

Если реальный сервер противоречит этому документу, сначала зафиксировать
пример запроса/ответа и только потом менять контракт библиотеки.

## Endpoint и transport

Примеры используют:

``` text
POST <rukovoditel-base>/api/rest.php
```

В старых примерах встречаются versioned paths вроде:

``` text
/product_2.5/api/rest.php
/product_3.6/api/rest.php
```

Поэтому библиотека должна принимать полный endpoint в конфигурации и не
конструировать его из base URL.

CRUD-примеры используют PHP `http_build_query`, то есть
`application/x-www-form-urlencoded`.

Отдельный пример `select` показывает `Content-Type: application/json` и
JSON body. Это подтверждает JSON как минимум для показанного сценария,
но **не доказывает**, что каждый action одинаково работает через JSON.

Для первой реализации предпочтителен form transport.

### Схема form POST

Все параметры находятся в **теле** одного POST к настроенному endpoint.
Это пары `имя=значение`, закодированные как
`application/x-www-form-urlencoded`. `key`, `username`, `password` и
`action` добавляются к каждому запросу. `entity_id` добавляется для
actions, которым нужна сущность. Endpoint может содержать собственный
query string (например, `demo_id`); клиент сохраняет его в URL, а
параметры action помещает в тело.

Для вложенного объекта используется PHP-нотация с квадратными скобками:

| Логическая структура | Имя form-параметра | Значение |
| --- | --- | --- |
| `items: {field_338: "Заявка"}` | `items[field_338]` | `Заявка` |
| `filters: {157: {value: 37}}` | `filters[157][value]` | `37` |
| `update_by_field: {id: [37, 38]}` | `update_by_field[id][0]`, `update_by_field[id][1]` | `37`, `38` |

Например, логический `insert` из раздела ниже превращается в form-тело
следующего вида (порядок пар не значим; реальные значения URL-кодируются):

```text
key=<KEY>&username=<USERNAME>&password=<PASSWORD>&action=insert&entity_id=34&items[field_338]=Заявка+Тест&items[field_426]=2017-12-29&items[field_429]=166%2C167
```

В этом фрагменте квадратные скобки показаны для чтения: на проводе
`url.Values.Encode` экранирует их как `%5B` и `%5D`. Пробел становится
`+`, запятая — `%2C`. Порядок пар в приведённой строке иллюстративный.
Это описание работы текущего клиента и документированных PHP-примеров,
а не утверждение о поддержке произвольных вложенных структур сервером.

Вот полный **схематический** HTTP-запрос для чтения полей сущности 39.
`<...>` означает значение из конфигурации, не буквально передаваемый
текст. Длину тела вычисляет HTTP-клиент.

```http
POST /api/rest.php HTTP/1.1
Content-Type: application/x-www-form-urlencoded
Accept: application/json

action=get_entity_fields&entity_id=39&key=<KEY>&password=<PASSWORD>&username=<USERNAME>
```

Реальный endpoint может включать другой путь и query string. Клиент
отправляет пары в лексикографическом порядке ключей; серверный контракт
не должен зависеть от их порядка. Пример вызова через Go:

```go
client, err := api.NewClient(api.Config{
    Endpoint: endpoint,
    Key: key,
    Username: username,
    Password: password,
})
if err != nil { /* обработать ошибку конфигурации */ }
data, err := client.GetEntityFields(ctx, 39)
if err != nil { /* обработать transport/HTTP/decode/API error */ }
// data — json.RawMessage; схема описана в FIELDS.md только для сервера 3.7.
_ = data
```

Пакет `internal/api` доступен Go-коду внутри родительского модуля;
внешний модуль не может импортировать его напрямую из-за правила Go
для каталогов `internal`.

`Client.Do` позволяет передать дополнительные параметры без отдельного
wrapper. Он запрещает переопределять `key`, `username`, `password`,
`action` и `entity_id` через `Params`. Формы параметров, которые ещё не
подтверждены, можно исследовать через `Do`, не добавляя их в типизированный
интерфейс. Пример ручного вызова: [`examples/lowlevel`](../examples/lowlevel/README.md).

## Общие параметры

Почти каждый запрос содержит:

  -----------------------------------------------------------------------
  Параметр                            Значение
  ----------------------------------- -----------------------------------
  `key`                               API key

  `username`                          пользователь, от имени которого
                                      выполняется действие

  `password`                          пароль

  `action`                            имя операции

  `entity_id`                         ID сущности; нужен только
                                      операциям, работающим с сущностью
  -----------------------------------------------------------------------

## Общий ответ

Успешный пример:

``` json
{
  "status": "success",
  "data": []
}
```

Успех операции определяется как:

``` text
status == "success"
```

Структура error response в доступной документации не описана.

В клиенте HTTP non-2xx возвращает `HTTPError` с кодом и сырым body.
Некорректный JSON в HTTP 2xx даёт ошибку декодирования. JSON envelope
со `status != "success"` возвращает `APIError`, который сохраняет сырой
body и `data`. Таким образом, HTTP 200 сам по себе не означает успешную
операцию. Текст ошибок клиента не содержит credentials; сырое body
может содержать данные, присланные сервером, и требует осторожного
обращения.

## Карта actions и методов клиента

`entity_id` указан отдельно от дополнительных form-параметров.
Значения `data` у metadata/process wrappers остаются `json.RawMessage`.

| Action | Метод `Client` | `entity_id` | Дополнительные параметры |
| --- | --- | --- | --- |
| `insert` | `Insert` | обязателен | `items[...]` |
| `select` | `Select` | обязателен | `limit`, `select_fields`, `reports_id`, `filters[...]`, `rows_per_page` — опциональны |
| `update` | `Update` | обязателен | `data[...]`, непустой `update_by_field[...]` |
| `delete` | `Delete` | обязателен | непустой `delete_by_field[...]` |
| `get_entities` | `GetEntities` | нет | нет |
| `get_entity_fields` | `GetEntityFields` | обязателен | нет; подробная схема наблюдавшегося `data` — [FIELDS.md](FIELDS.md) |
| `get_field_choices` | `GetFieldChoices` | обязателен | `field_id`; наблюдавшиеся варианты — [FIELDS.md](FIELDS.md) |
| `get_global_lists` | только `Do`; отложено | нет | нет |
| `get_global_list_choices` | только `Do`; отложено | нет | `list_id` |
| `get_process_buttons` | `GetProcessButtons` | обязателен | `item_id` опционален |
| `run_process` | `RunProcess` | обязателен | `item_id`, `process_id` |

Методы metadata/process в текущем scope формируют документированные параметры, но сейчас
не валидируют существование ID на сервере. Нулевой ID не означает
подтверждённый сервером способ запросить «все»: если нужно исследовать
необычное значение, используйте `Do`. Для запуска этих методов с
явными ID есть [`examples/metadata`](../examples/metadata/README.md).

# Поля записей

Пользовательское поле при записи именуется:

``` text
field_<FIELD_ID>
```

Пример:

``` text
field_338
```

Значение поля API принимает в строковом виде согласно документации.

Системные поля, упомянутые документацией:

``` text
id
parent_item_id
date_added
date_updated
created_by
password
```

Не все системные поля допустимы во всех actions.

## Дата

Формат значения при записи:

``` text
YYYY-MM-DD
```

Пример:

``` text
2017-12-29
```

## Выпадающий список

Одиночный выбор: ID option.

Множественный выбор: ID через запятую.

``` text
166,167
```

Для global list используется ID option из global list.

## Вложения

Значение --- HTTP-ссылка на файл.

Несколько файлов --- ссылки через запятую.

# insert

## Request

``` text
action=insert
entity_id=<ENTITY_ID>
items[...]=...
```

Пример логической структуры:

``` json
{
  "action": "insert",
  "entity_id": 34,
  "items": {
    "field_338": "Заявка Тест",
    "field_426": "2017-12-29",
    "field_429": "166,167"
  }
}
```

`parent_item_id` внутри `items` опционален и нужен при добавлении записи
в родительскую запись.

Сущность 39 на проверенном сервере создаётся в контексте родительской
записи. В предоставленном примере **веб-формы** присутствовали
`parent_item_id=1366` и путь, оканчивающийся на `/39`. Это был
`multipart/form-data` запрос веб-интерфейса с параметрами `fields[...]`,
а не запрос REST API; его session token, `demo_id`, upload-поле и
параметры redirect не относятся к документированному REST `insert`.
Для REST использован документированный `items[parent_item_id]`.
Значения веб-формы для поля даты были в формате `DD.MM.YYYY HH:MM`,
тогда как успешный REST probe отправил `YYYY-MM-DD`; эти форматы нельзя
отождествлять.

Для тестовой сущности 39 на сервере 3.7 поля с
`is_required="1"` определяются через `get_entity_fields`; на момент
probe это 418, 420, 423 и 426. Список зависит от конфигурации
конкретной сущности. Подробности: [FIELDS.md](FIELDS.md#как-узнать-поля-помеченные-обязательными).

## Response

Документированный успешный `data`:

``` json
{
  "id": 119
}
```

На тестовом сервере 3.7 успешный `insert` сущности 39 вернул объект с
**строковым** `id`. Поэтому `Client.Insert` принимает и JSON-число из
документированного примера, и десятичную JSON-строку, преобразуя её в
`InsertResult.ID int64`. Это наблюдение не меняет форматы других ID в
ответах API.

Несмотря на формулировку документации «ID добавленных записей», пример
подтверждает только вставку одной записи и одно поле `id`.

**Не считать batch insert подтверждённым.**

# select

## Request

``` text
action=select
entity_id=<ENTITY_ID>
```

Опциональные параметры:

  Параметр          Назначение
  ----------------- -------------------------------------------------
  `limit`           ограничение числа строк; пример использует `0`
  `select_fields`   CSV ID полей, например `338,388`
  `reports_id`      ID отчёта; применяются его фильтры и сортировка
  `filters`         пользовательские фильтры
  `rows_per_page`   число строк на страницу

Документация повторно называет параметр текущей страницы `filters`, что
выглядит как ошибка. **Имя параметра страницы неизвестно и требует
проверки.**

Если `select_fields` отсутствует, документация обещает значения всех
полей.

## Filters

### Диапазон дат

``` text
filters[159]=2018-05-10,2018-05-16
```

Допускается открытая граница:

``` text
2018-05-10,
```

### List include/exclude

Логическая структура:

``` json
{
  "157": {
    "value": 37,
    "condition": "include"
  }
}
```

`condition`: - `include`; - `exclude`.

### Числовое сравнение

``` text
filters[203]=>30
```

То есть comparison operator кодируется непосредственно в строковом
значении.

### Empty / not empty

``` json
{
  "203": {
    "condition": "not_empty_value"
  }
}
```

Документированы: - `empty_value`; - `not_empty_value`.

### Search

``` json
{
  "158": {
    "value": "keywords",
    "condition": "search"
  }
}
```

### Системные поля

В filters разрешены в том числе:

``` text
id
parent_item_id
date_added
date_updated
```

Пример:

``` text
filters[id]=13,14
```

## Response

Документированный пример записи:

``` json
{
  "id": 112,
  "date_added": "01/15/2018 10:42",
  "created_by": "Kharchishin Sergey",
  "338": "Заявка 6",
  "388": "Новая"
}
```

Важно: пользовательские поля в этом примере возвращаются как `"338"`,
`"388"`, **без префикса `field_`**.

Формат даты в response отличается от формата даты при записи. Не парсить
дату на internal-уровне без дополнительной необходимости.

# get_entities

Доступно начиная с документации для версии 3.3.

Request:

``` text
action=get_entities
```

`entity_id` не требуется.

Формат `data` в доступном фрагменте документации не указан.

Метод: `GetEntities(ctx)`. На одном тестовом сервере 3.7 наблюдался
массив объектов. Первый объект имел ключи `group_id`, `group_name`,
`id`, `level`, `name`, `notes`, `parent_id`, `path`, `sort_order`.
Подробности и пределы наблюдения — в таблице probe ниже.

Обезличенная **форма первого элемента** `data` (остальные 37 элементов
опущены; строки заменены масками):

```json
{
  "id": "<удалено>",
  "parent_id": "<удалено>",
  "group_id": "<удалено>",
  "group_name": null,
  "name": "<удалено>",
  "notes": "<удалено>",
  "sort_order": "<удалено>",
  "level": 0,
  "path": []
}
```

`level: 0` и пустой `path` показывают только JSON-типы, не фактические
значения ответа. У первого наблюдавшегося элемента `path` был массивом,
а `group_name` — `null`; это не определяет типы этих полей у всех
элементов.

# get_process_buttons

Request:

``` text
action=get_process_buttons
entity_id=21
```

Опционально:

``` text
item_id=1
```

Формат `data` не указан.

Метод: `GetProcessButtons(ctx, entityID, itemID)`. `nil` для `itemID`
означает отсутствие form-параметра, указатель на ID — его передачу.
На сервере 3.7 с `item_id=1` и без него наблюдались массивы объектов
процесса. Совпадение ID в этих двух ответах не доказывает, что параметр
никогда не фильтрует кнопки.

На том сервере без `item_id` получено 2 объекта для сущности 1 и 8 для
сущности 39. Первый объект каждого ответа имел одинаковый набор из 33
ключей; **все его значения были строками**. Ниже приведены только
имена ключей, сгруппированные для чтения, без предположения об их
значении или допустимых значениях:

| Группа для чтения | Наблюдавшиеся ключи первого объекта |
| --- | --- |
| Идентификаторы и подписи | `id`, `entities_id`, `name`, `button_title`, `submit_button_title`, `notes` |
| Отображение | `button_position`, `button_color`, `button_icon`, `window_width`, `hide_entity_name`, `print_template` |
| Доступ и исполнители | `users_groups`, `assigned_to`, `assigned_to_all`, `access_to_assigned` |
| Подтверждение и результат | `confirmation_text`, `warning_text`, `success_message`, `success_message_status`, `redirect_to_items_listing` |
| Настройки формы и полей | `allow_comments`, `disable_comments`, `apply_fields_access_rules`, `apply_fields_display_rules`, `is_form_wizard`, `is_form_wizard_progress_bar` |
| Прочие настройки | `preview_prcess_actions`, `payment_modules`, `javascript_in_from`, `javascript_onsubmit`, `is_active`, `sort_order` |

Имена `preview_prcess_actions` и `javascript_in_from` приведены ровно
как в ответе сервера 3.7; клиент их не исправляет. Не следует считать
строковый JSON-тип каждого из этих ключей стабильным для других
процессов или версий.

# Неизвестности, которые нужно проверить на реальном сервере

1.  Точная структура error responses.
2.  Форматы `data` у metadata actions в текущем scope; global lists
    вынесены в будущую доработку.
3.  Форматы `data` у `get_process_buttons` и `run_process`.
4.  Реальное имя параметра номера страницы для `select`.
5.  Семантика `limit=0`.
6.  Поддержка JSON transport всеми actions или только частью API.
7.  Поддерживается ли batch insert.
8.  Точные JSON-типы ID и значений: number/string могут различаться.
9.  Поведение пустых/null значений.
10. Различия API между используемыми версиями Rukovoditel.

### Успешный `insert → select → delete → select` с родителем (2026-10-09)

Предоставленный пример создания задачи через веб-форму показал

## План проверки на реальном сервере

Все сценарии запускать вручную с явным opt-in на тестовом сервере.
Записать версию Rukovoditel, полный путь endpoint без credentials,
action, параметры и сырой HTTP status/body после удаления персональных
данных и секретов. Для каждого вывода указать версию и сценарий; один
ответ не доказывает поведение других версий. Сначала выполнить сценарии
через form transport. Обычный `go test ./...` к серверу не обращается.

| Сценарий | Что отправить | Что проверить и зафиксировать |
