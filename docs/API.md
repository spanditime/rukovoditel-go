# Rukovoditel REST API --- известный контракт

Этот документ фиксирует **только информацию, доступную из текущей
документации Rukovoditel и предоставленных примеров**. Он нужен прежде
всего для реализации Go-клиента.

Если реальный сервер противоречит этому документу, сначала зафиксировать
пример запроса/ответа и только потом менять контракт библиотеки.

## Endpoint и transport

Примеры используют:

``` text
POST <rukovoditel-base>/api/rest.php
```

В старых примерах встречаются versioned paths вроде:

``` text
/product_2.5/api/rest.php
/product_3.6/api/rest.php
```

Поэтому библиотека должна принимать полный endpoint в конфигурации и не
конструировать его из base URL.

CRUD-примеры используют PHP `http_build_query`, то есть
`application/x-www-form-urlencoded`.

Отдельный пример `select` показывает `Content-Type: application/json` и
JSON body. Это подтверждает JSON как минимум для показанного сценария,
но **не доказывает**, что каждый action одинаково работает через JSON.

Для первой реализации предпочтителен form transport.

## Общие параметры

Почти каждый запрос содержит:

  -----------------------------------------------------------------------
  Параметр                            Значение
  ----------------------------------- -----------------------------------
  `key`                               API key

  `username`                          пользователь, от имени которого
                                      выполняется действие

  `password`                          пароль

  `action`                            имя операции

  `entity_id`                         ID сущности; нужен только
                                      операциям, работающим с сущностью
  -----------------------------------------------------------------------

## Общий ответ

Успешный пример:

``` json
{
  "status": "success",
  "data": []
}
```

Успех операции определяется как:

``` text
status == "success"
```

Структура error response в доступной документации не описана.

# Поля записей

Пользовательское поле при записи именуется:

``` text
field_<FIELD_ID>
```

Пример:

``` text
field_338
```

Значение поля API принимает в строковом виде согласно документации.

Системные поля, упомянутые документацией:

``` text
id
parent_item_id
date_added
date_updated
created_by
password
```

Не все системные поля допустимы во всех actions.

## Дата

Формат значения при записи:

``` text
YYYY-MM-DD
```

Пример:

``` text
2017-12-29
```

## Выпадающий список

Одиночный выбор: ID option.

Множественный выбор: ID через запятую.

``` text
166,167
```

Для global list используется ID option из global list.

## Вложения

Значение --- HTTP-ссылка на файл.

Несколько файлов --- ссылки через запятую.

# insert

## Request

``` text
action=insert
entity_id=<ENTITY_ID>
items[...]=...
```

Пример логической структуры:

``` json
{
  "action": "insert",
  "entity_id": 34,
  "items": {
    "field_338": "Заявка Тест",
    "field_426": "2017-12-29",
    "field_429": "166,167"
  }
}
```

`parent_item_id` внутри `items` опционален и нужен при добавлении записи
в родительскую запись.

## Response

Документированный успешный `data`:

``` json
{
  "id": 119
}
```

Несмотря на формулировку документации «ID добавленных записей», пример
подтверждает только вставку одной записи и одно поле `id`.

**Не считать batch insert подтверждённым.**

------------------------------------------------------------------------

# select

## Request

``` text
action=select
entity_id=<ENTITY_ID>
```

Опциональные параметры:

  Параметр          Назначение
  ----------------- -------------------------------------------------
  `limit`           ограничение числа строк; пример использует `0`
  `select_fields`   CSV ID полей, например `338,388`
  `reports_id`      ID отчёта; применяются его фильтры и сортировка
  `filters`         пользовательские фильтры
  `rows_per_page`   число строк на страницу

Документация повторно называет параметр текущей страницы `filters`, что
выглядит как ошибка. **Имя параметра страницы неизвестно и требует
проверки.**

Если `select_fields` отсутствует, документация обещает значения всех
полей.

## Filters

### Диапазон дат

``` text
filters[159]=2018-05-10,2018-05-16
```

Допускается открытая граница:

``` text
2018-05-10,
```

### List include/exclude

Логическая структура:

``` json
{
  "157": {
    "value": 37,
    "condition": "include"
  }
}
```

`condition`: - `include`; - `exclude`.

### Числовое сравнение

``` text
filters[203]=>30
```

То есть comparison operator кодируется непосредственно в строковом
значении.

### Empty / not empty

``` json
{
  "203": {
    "condition": "not_empty_value"
  }
}
```

Документированы: - `empty_value`; - `not_empty_value`.

### Search

``` json
{
  "158": {
    "value": "keywords",
    "condition": "search"
  }
}
```

### Системные поля

В filters разрешены в том числе:

``` text
id
parent_item_id
date_added
date_updated
```

Пример:

``` text
filters[id]=13,14
```

## Response

Документированный пример записи:

``` json
{
  "id": 112,
  "date_added": "01/15/2018 10:42",
  "created_by": "Kharchishin Sergey",
  "338": "Заявка 6",
  "388": "Новая"
}
```

Важно: пользовательские поля в этом примере возвращаются как `"338"`,
`"388"`, **без префикса `field_`**.

Формат даты в response отличается от формата даты при записи. Не парсить
дату на internal-уровне без дополнительной необходимости.

------------------------------------------------------------------------

# update

## Request

``` text
action=update
entity_id=<ENTITY_ID>
data[...]=...
update_by_field[...]=...
```

`data` --- поля, которые нужно изменить.

Документация отдельно разрешает обновлять системные поля:

``` text
created_by
parent_item_id
password
```

Примеры criteria:

Одна запись:

``` text
update_by_field[id]=37
```

Несколько ID логически:

``` json
{
  "id": [37, 38]
}
```

По пользовательскому полю:

``` text
update_by_field[field_156]=34
```

Update по пользовательскому полю потенциально обновляет несколько
записей.

Формат успешного `data` не описан.

------------------------------------------------------------------------

# delete

## Request

``` text
action=delete
entity_id=<ENTITY_ID>
delete_by_field[...]=...
```

Примеры:

``` text
delete_by_field[id]=37
```

или несколько ID:

``` json
{
  "id": [37, 38]
}
```

или по пользовательскому полю:

``` text
delete_by_field[field_156]=34
```

Delete по пользовательскому полю потенциально удаляет несколько записей.

Формат успешного `data` не описан.

# Неизвестности, которые нужно проверить на реальном сервере

1.  Точная структура error responses.
2.  Форматы `data` у metadata actions.
3.  Форматы `data` у `get_process_buttons` и `run_process`.
4.  Реальное имя параметра номера страницы для `select`.
5.  Семантика `limit=0`.
6.  Поддержка JSON transport всеми actions или только частью API.
7.  Поддерживается ли batch insert.
8.  Точные JSON-типы ID и значений: number/string могут различаться.
9.  Поведение пустых/null значений.
10. Различия API между используемыми версиями Rukovoditel.

При получении реальных примеров добавлять сюда обезличенный
request/response и помечать соответствующий пункт как подтверждённый.

## План проверки на реальном сервере

Все сценарии запускать вручную с явным opt-in на тестовом сервере.
Записать версию Rukovoditel, полный путь endpoint без credentials,
action, параметры и сырой HTTP status/body после удаления персональных
данных и секретов. Для каждого вывода указать версию и сценарий; один
ответ не доказывает поведение других версий. Сначала выполнить сценарии
через form transport. Обычный `go test ./...` к серверу не обращается.

| Сценарий | Что отправить | Что проверить и зафиксировать |
| --- | --- | --- |
| Envelope и ошибки | Валидный `select`, затем заведомо неверный action/ID на тестовом сервере | HTTP status, `status`, наличие и форма `data`, полный обезличенный error body; отдельно различить ошибку API от не-2xx. |
| Metadata | `get_entities`, `get_entity_fields`, `get_field_choices`, `get_global_lists`, `get_global_list_choices` с существующими ID | Для каждого action — допустимость параметров, JSON-тип и фактическая структура `data`, пустой результат. |
| Чтение | `select` без фильтра, с `select_fields`, каждым видом `filters`, `reports_id` | Ключи пользовательских/системных полей, JSON-типы ID и значений, пустые/null, влияние отчёта и фильтров. Проверять результат на заранее известных записях. |
| Pagination | Набор с известным количеством записей, разные `rows_per_page` и `limit`, включая `0`; кандидат имени параметра страницы — только через низкоуровневый `Do` | Сравнить ID страниц, повторы и пропуски, фактическую семантику `limit=0`; не типизировать имя страницы до подтверждения. |
| Запись | `insert` одной тестовой записи, `select` по её ID, `update` по этому ID, повторный `select`, затем `delete` по этому ID и контрольный `select` | Тело запроса (`items`, `data`, `*_by_field`), `data.id`, формат успешного `data` у update/delete, фактическое изменение и удаление. Проверить поле даты, одиночный/множественный выбор и пустое значение, если есть безопасные тестовые поля. |
| Множественные criteria | Несколько специально созданных тестовых записей; `update_by_field[id][0..]` и `delete_by_field[id][0..]`; отдельно критерий по тестовому пользовательскому полю | Какие записи затронуты, формат ответа и поведение при отсутствии совпадений. Не использовать общие данные. |
| Process | `get_process_buttons` с/без `item_id`; `run_process` только для заранее подготовленного безопасного процесса | Структура `data`, обязательность параметров и наблюдаемый эффект; если безопасного процесса нет, оставить `run_process` непроверенным. |
| JSON | Только если нужен JSON transport: повторить безопасный `select`; для других actions — отдельные проверки по необходимости | Какие именно actions и версия принимают JSON; не обобщать результат одного action. |

Batch insert не проверять в основном CRUD probe: он не документирован.
Если появится практическая необходимость, исследовать отдельно на
изолированной сущности и не расширять публичный контракт до фиксации
реального ответа.

После каждого сценария добавить минимальный обезличенный request/response
fixture и отметить соответствующий пункт списка неизвестностей как
подтверждённый для указанной версии либо оставить открытым с причиной.
